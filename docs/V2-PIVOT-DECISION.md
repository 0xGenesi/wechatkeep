## 1. 决策点的由来（76 轮终审）

v2-as-designed（外科式：保留 newmsgid + NOP 下游删除）经真机 A/B 终审死亡：
revokemessage 链真实身份 = 撤回后重新编辑资格记账（ReEditStatus），不在原生
撤回显示路径。原生删除执行体仍未找到（排除面 = drive28-36 七簇 + 本链）。
三案：(a) WCDB 层继续 RE；(b) runtime 合成群聊 tip；(c) 接受 v1 现状。

## 3. 逐案重评

### (a) WCDB 层继续 RE 找原生删除点 — **不推荐（关闭）**
- 排除面已 8 簇；Windows 孪生证据表明 revokemessage 表的 DELETE 是清理族；
  原生删除很可能走内存层直改+同步（不经 WCDB SQL 文本层），继续找 = 无底洞。
- 即便找到，v2-as-designed 的死因（链图对≠链路对）提示：下一个「找到的链」
  仍需真机 A/B 验证，成本循环。
- 机会成本：同一投入在 T5/Windows 新仓上回报更高。

### (b) runtime 群聊 tip — 拆三层，**默认层已可能免费**
- **b0（现状即所求）**：keep_message（XML 数值清零）在群聊的静态预测 =
  handler 不早退 → svrid=0 查找失败 → notice 从 replacemsg 构造 → **群 tip
  照常显示（服务端原文，诚实）**。本轮 0x3089b64 序列支持该预测。
  T5 Phase 4 = 实证（成本已沉没，本就是 runbook 的一步）。
- **b2（post-parse 键策略，备选）**：若 b0 意外失败（群 tip 不显示），备选 =
  hook parse **返回**（而非入口）清 struct+0x1C8——前提 = tip 锚定发生在
  parse 内、删除消费在 handler 内（⑰ 已给出两处地址，顺序核验为持久工程
  分钟级增量）。成本中，不改写 XML、不动消息内容。
- **b1（完整合成，76 轮的原 b）**：进程内构造并插入本地 tip 消息。插入点
  候选（handler notice 构造）虽已现形，但 C++ 对象构造 + 会话路由的稳定
  性风险与更新脆性最高。**仅当 b0 失败且 b2 核验不可行时启用**。

### (c) 接受现状 — **与 b0 合流**
- ㉓ 之后「现状」已比 76 轮时好：群聊数据层同构已证。若 T5 Phase 4 确认
  群 tip 显示，c 即用户得到完整体验（消息保留 + 群/私诚实 tip + 私聊自定义
  文案 + 群聊自定义文案待渲染校验通过）。

## 4. 决策规则（建议）

```
T5 Phase 4（已 in runbook，零额外成本）：
├─ 群 tip 显示（含自定义文案）→ 决策 = c（=b0 免费达成）；b/a 全关闭
├─ 群 tip 不显示 → 30 分钟静态核 b2 前提（tip 锚定 vs 删除消费的顺序）
│   ├─ 顺序成立 → 决策 = b2（一个 parse 返回 hook 的增量）
│   └─ 顺序不成立 → 决策 = b1 立项评审（对照 Windows 新仓优先级）
└─ 渲染破坏（R2-R5）→ 先归因表收窄机制，tip 议题顺延（前置=T5 机制关账）
```

**对 76 轮建议 b 的修正**：b 的「合成」表述建立在「群 tip 需要无中生有」的
前提上；㉒/㉓ 证明服务端已下发全部 tip 文本、客户端管线只差一个未被证明的
失败——**大概率无需合成，现状即目标态**。决策从「三选一」压缩为
「T5 Phase 4 的一个观测 + 一条 if」。
